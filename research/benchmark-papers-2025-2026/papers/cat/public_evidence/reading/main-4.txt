4. Evaluation
Our approach (CAT) incorporates call-chain information to explicitly model external dependencies in LLM-based project-level test generation. As discussed earlier, PANTA represents a recent, state-of-the-art LLM-based project-level testing framework that iteratively provides uncovered execution paths of the focal class as feedback to guide test generation toward higher coverage. However, PANTA does not explicitly capture cross-module dependencies, resulting in degraded performance for classes with rich external dependencies.
In our evaluation, we compare CAT with the original PANTA on the same benchmark, Defects4J.
Unlike CAT, which generates tests for each focal method individually, PANTA generates tests at the focal-class level, producing tests for all focal methods within a class in a single run. As a result, even though CAT uses fewer iterations per focal method than PANTA, the total number of generation iterations can be substantially larger when aggregated at the class level. For example, while PANTA may perform 30 iterations for a single focal class, a class containing 20 focal methods would require CAT to perform 200 iterations if tests for each method are generated with 10 iterations. This naturally leads to a higher overall time cost.
To ensure a fair comparison, we also include a time-bounded variant of PANTA, denoted PANTAtb, constrained by the same time budget as CAT. To quantify the contribution of static analysis in CAT, we also report the performance of CATvanilla, whose prompts exclude the execution context extracted in Section 3.2.
Since modern LLMs are trained on large-scale public code repositories, Defects4J projects may partially overlap with their training corpora. This overlap could inflate results due to data leakage or memorization. Although both CAT and the baseline (originally evaluated on Defects4J) are equally affected by this issue, we also evaluate them on projects not included in the LLM’s training data. This ensures our results reflect realistic performance on truly unseen code and better demonstrate the practical utility of our approach.
Moreover, these additional projects are structurally more complex than those in Defects4J. As discussed in Section 4.1.1, the Defects4J projects are organized as single-module repositories, where classes are primarily located within a single source directory, and dependencies are mainly inter-class. In contrast, the new projects are multi-module repositories involving multiple source directories and more complex dependencies across both classes and modules. Evaluating on these projects therefore not only reduces the risk of training data leakage but also provides stronger evidence of CAT’s generalization ability in more realistic, challenging repository-level testing scenarios.
To summarize, our evaluation is designed to answer the following research questions:
•
RQ1: How does CAT compare with existing test generation approaches in terms of effectiveness, efficiency, and generated test characteristics?
•
RQ2: To what extent do call-chain awareness and dependency context contribute to CAT’s effectiveness, particularly through indirect invocations?
•
RQ3: How does CAT perform on projects that are not included in the training data of the underlying LLM, and how does it compare with existing approaches?
RQ1 compares overall effectiveness and efficiency with PANTA and its time-bounded variant PANTAtb, and compares effectiveness with EvoSuite. RQ2 investigates the contribution of call-chain and dependency contexts through ablation analysis. RQ3 examines CAT’s generalization ability on unseen and more complex multi-module projects.

4.1.2. Process
The static analysis of CAT is performed offline as a one-time preprocessing step before test generation. For each focal method, we extract its call-chain and dependency contexts as described in Section 3.2. This preprocessing takes 8.35 hours for the 2,971 focal methods in Defects4J and 61.63 hours for the 2,707 focal methods in the unseen projects. Once CAT extracts contexts for all focal methods, it proceeds to the LLM-based generation and fixing phases, reusing the precomputed contexts across iterations without repeating the static analysis. We therefore report this preprocessing cost separately rather than including it in the end-to-end test generation time.
To address RQ1, we first run the original PANTA with its default configuration on the Defects4J dataset using the provided scripts, selecting 14 projects for evaluation. As in the evaluation of PANTA (Gu et al., 2025), tests are generated without existing tests: the test class of each focal class is removed before generation.
Next, we conducted a preliminary experiment on a random sample of 20 focal methods from all projects. We observed that after 10 iterations, CAT coverage improvement becomes marginal. Accordingly, we set the number of iterations for CAT to 10 (Ng​e​n=10N_{gen}=10) for all focal methods across all projects. We apply the same iteration setting to CATpath, our variant that augments CAT with the uncovered-path information used in PANTA, to ensure comparability.
Notably, PANTA generates tests for all focal methods within a class in a single run, using the maximum cyclomatic complexity as the number of iterations, which is typically much higher than 10. As shown in Table 1, the average maximum cyclomatic complexity (CYCmax) for the selected methods under test in the Defects4J projects is 27, ranging from 11 to 37.
To ensure a fair comparison, we also run PANTA with a maximum of 100 iterations and impose a class-specific time budget equal to the time CAT consumes on the corresponding focal class. We terminate PANTA once this time budget is reached, yielding a time-constrained variant denoted PANTAtb. As an additional exploratory analysis, we further evaluate CATpath under the same iteration and time budget settings as CAT to examine whether combining uncovered-path information with call-chain and dependency context yields further gains.
We report line and branch coverage measured by JaCoCo (JaCoCo Developers, ), as well as mutation scores computed by PITest (PIT Developers, ), to assess defect-detection effectiveness, following established practices in prior work (Wang et al., 2025; Xu et al., 2025; Harman et al., 2025). Additionally, we use PITest with its DEFAULTS mutation operator group to measure each test suite’s mutation score. The DEFAULTS group comprises mutation operators commonly adopted in the literature (Fraser and Arcuri, 2015; Wang et al., 2026). According to the official PITest documentation, these operators are designed to generate mutants that are relatively difficult for tests to detect while limiting the generation of equivalent mutants.
All metrics are computed on each approach’s final test suite, comprising the tests retained after all generation and repair iterations. Following PANTA, we compute these metrics at the focal-class level. For each focal class, we combine all retained tests for its focal methods and obtain line and branch coverage from the corresponding JaCoCo reports. Mutation scores are computed using PITest, with the focal classes specified as mutation targets. The value reported for a project is the mean over its focal classes. We apply the same measurement procedure to CAT, its variants, and all baselines.
In addition to coverage and mutation score, we report the total number of LLM tokens consumed, end-to-end test generation time, the number of retained test methods, and the proportion of retained test methods that use a mocking framework. The total token consumption includes both input and output tokens across all LLM calls made during test generation and repair. End-to-end time measures the wall-clock time from the first LLM invocation to the final test suite, including LLM inference, test repair, compilation, and test execution. It excludes the static-analysis phase used to construct call-chain and dependency contexts, since this analysis runs offline as a one-time preprocessing step and its results can be reused throughout test generation. The number of retained tests is the number of test methods remaining in the final test suite after all generation and repair iterations. CAT retains every test that compiles and passes, including tests that do not increase coverage, and does not remove duplicated tests; PANTA likewise adds every passing test to its test file (Gu et al., 2025). The reported number of retained tests may therefore include duplicated tests, which we did not measure; since a duplicated test executes the same code and checks the same behavior as the test it duplicates, it can inflate the test count but not coverage or the mutation score. To measure the use of mocking, we inspect each retained test method and classify it as using mocking if the method itself, or its test setup required for execution, invokes APIs from the adopted mocking framework (e.g., Mockito). We then compute the mocking rate as the number of retained test methods using mocking divided by the total number of retained test methods. We apply the same metrics and measurement procedures to RQ3. To further analyze API hallucinations, we examined the compilation diagnostics and test execution results of all tests generated by CAT on the Defects4J projects, checked the referenced program elements against the project source code, classified the identified hallucinations into two main categories reported in detailed results, and calculated the percentage of all generated tests affected by each category.
To address RQ2, we construct three variants of CAT, denoted as CATvanilla, CATchain, and CATdep, by disabling both call-chain awareness and dependency resolution, retaining only call-chain awareness, and retaining only dependency resolution, respectively, as described in Section 3.2. Specifically, we remove the corresponding contextual information from both the generation and fixing prompts described in Sections 3.3 and 3.4. We evaluate these variants on Defects4J using the same configuration and evaluation metrics as CAT in RQ1, allowing us to isolate the individual and combined contributions of call-chain awareness and dependency resolution. We further examine the role of indirect invocations enabled by call-chain awareness. Specifically, we quantify the proportion of retained tests that invoke their focal methods indirectly through the extracted call chains and measure the coverage and mutation-score improvements attributable to these tests.
To address RQ3, we first collect metadata (i.e., class complexity and focal methods within each class) for the four unseen projects described in Section 4.1.1. Since these projects are multi-module and differ from Defects4J, we adapt the evaluation scripts to support multi-module project structures. We then evaluate CAT on the selected target classes. For comparison, we also run PANTA and PANTAtb under the same settings.
In RQ1 and RQ3, we additionally compare against EvoSuite using a strong configuration informed by prior studies. Specifically, we use DynaMOSA as the search algorithm, following its empirical evaluation in prior work (Campos et al., 2017) and its adoption in subsequent EvoSuite-based studies (Panichella et al., 2022). We further enable private-API access through reflection and functional mocking, which have been shown to facilitate constructing program states that are difficult to reach through public APIs alone (Arcuri et al., 2017), and we use a mutation-based strategy for assertion generation. We allocate a generous search budget of 900 seconds per run and focal class, substantially exceeding EvoSuite’s default search budget of 60 seconds and the budgets commonly adopted in prior studies (Campos et al., 2017; Panichella et al., 2022). EvoSuite 1.2.0 is executed under the same Java/JDK environment as the other approaches, while the remaining parameters retain their default settings. Since its search is randomized, we run it three times per focal class with different random seeds and report the average line coverage, branch coverage, and mutation score over the three runs. We do not include EvoSuite in the comparison of LLM token consumption, end-to-end generation time, mocking rate, or the number of retained tests. Token consumption is not applicable because EvoSuite does not rely on LLM inference. Its generation time is determined by a fixed search budget and is therefore not directly comparable to the iterative LLM-based generation process; moreover, we intentionally provide EvoSuite with a substantially larger budget of 900 seconds to avoid disadvantaging it. Similarly, EvoSuite incorporates functional mocking as an intrinsic test-generation mechanism, making its use of mocks conceptually different from mocks generated by the LLM-based approaches. We therefore use EvoSuite primarily as a reference baseline for comparing the effectiveness of the generated test suites: line coverage, branch coverage, and mutation score.
When comparing coverage and mutation scores, we report differences in percentage points (pp) and give the relative improvement over the baseline, (a−b)/b(a-b)/b, in parentheses.
