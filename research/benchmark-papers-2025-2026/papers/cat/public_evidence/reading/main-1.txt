Abstract.
Large language models (LLMs) have recently shown strong potential for generating project-level unit tests. However, existing state-of-the-art approaches primarily rely on execution-path information to guide prompt construction, which is often insufficient for complex software systems with rich inter-class dependencies, deep call chains, and intricate object initialization requirements. In this paper, we present CAT, a novel call-chain-aware LLM-based test generation approach that explicitly incorporates call-chain and dependency contexts into prompts through dedicated static analysis. To construct executable, semantically valid test contexts, CAT systematically models caller–callee relationships, object constructors, and third-party dependencies, and supports iterative test fixing when generation failures occur. We evaluate CAT on the widely used Defects4J benchmark and on four real-world GitHub projects released after the LLM’s cut-off date, and compare it with the state-of-the-art LLM-based approach PANTA and the search-based tool EvoSuite. The results show that, across projects in Defects4J, CAT improves line coverage, branch coverage, and mutation score by 12.52, 12.97, and 14.39 percentage points (18.02%, 21.52%, and 26.94% relative), respectively, over PANTA, and by 9.67, 4.17, and 15.70 percentage points (13.37%, 6.04%, and 30.13% relative) over EvoSuite. On the post-cutoff projects, CAT also achieves the highest average line coverage, branch coverage, and mutation score among all compared approaches. An ablation study further demonstrates the importance of call-chain and dependency contexts in CAT.

1. Introduction
Unit tests play a fundamental role in ensuring software quality and reliability. However, writing high-quality unit tests remains labor-intensive and requires substantial domain knowledge, posing a long-standing challenge for software engineers (Fraser and Arcuri, 2011; Tillmann and De Halleux, 2008; Tufano et al., 2019; Pacheco and Ernst, 2007). To mitigate this burden, a variety of automated test generation techniques have been proposed, including random testing (e.g., Randoop (Pacheco and Ernst, 2007)), search-based testing (e.g., EvoSuite (Fraser and Arcuri, 2011)), and symbolic execution–based approaches (e.g., KLEE (Cadar et al., 2008) and Pex (Tillmann and De Halleux, 2008)). These techniques have proven effective at detecting critical defects by systematically exploring program behaviour.
These techniques differ in how they obtain test inputs. Random testing extends random sequences of method calls using execution feedback; search-based testing evolves test suites towards coverage goals; and symbolic execution derives inputs by solving path constraints. Their test oracles are typically inferred from observed executions or from generic properties (e.g., crashes and contracts). KLEE and Pex target C and .NET programs, respectively, whereas Randoop and EvoSuite focus on unit test generation for Java—the setting studied in this paper. We include EvoSuite as a non-LLM baseline in our evaluation (Section 4) because it is commonly used as the reference non-LLM tool in recent studies of LLM-based test generation (Tang et al., 2024; Yang et al., 2024; Wang et al., 2024; Pan et al., 2025; Abdullin et al., 2025) and has outperformed Randoop in coverage, mutation score, and real-fault detection (Devroey et al., 2023; Shamshiri et al., 2015; Almasi et al., 2017).
More recently, advances in machine learning and large language models (LLMs) have further pushed the frontier of automated test generation (Wang et al., 2024; Pan et al., 2025; Nan et al., 2025). LLM-based approaches leverage learned programming knowledge and contextual reasoning to generate readable, functional test cases, significantly improving both the automation and effectiveness of testing.
Despite these advances, most existing work focuses on method-level (Wang et al., 2025; Xu et al., 2025; Ryan et al., 2024) or class-level (Gu et al., 2025; Zhang et al., 2024) test generation, which typically considers only the program logic within a single module. In contrast, project-level test generation, which must account for complex interprocedural dependencies, execution contexts, and interactions across multiple modules, remains largely underexplored and challenging. This gap limits the applicability of current techniques in large-scale software systems.
State-of-the-art project-level test generation approaches leverage execution-path feedback to iteratively guide LLMs toward uncovered code regions, including PANTA (Gu et al., 2025), PALM (Wu et al., 2026), and SymPrompt (Ryan et al., 2024). These approaches dynamically collect uncovered execution paths or path constraints to guide test generation toward higher coverage. While such strategies have demonstrated promising results in certain settings, they rely on incorporating uncovered execution paths into the prompt as feedback signals and generally do not explicitly model dependencies across modules and execution contexts, as illustrated in Listing 1, where inter-class dependencies are required to correctly invoke the focal method but are not captured by existing methods. As a result, they often fail to generate valid tests for projects with complex inter-module dependencies.
Empirical results in Section 4 further confirm this limitation. Using PANTA as a state-of-the-art representative of this line of work, we observe that on the JxPath project from the Defects4J (Just et al., 2014) dataset–where methods heavily depend on external dependencies (e.g., dependencies on other modules, third-party libraries)–it achieves only 56.97% line coverage and 53.88% branch coverage.
This observation suggests that the key difficulty lies not in identifying uncovered code locations but in constructing valid execution contexts, such as cross-class dependency setups, object initializations, and call sequences required to invoke the focal method. However, existing path-guided approaches provide limited insight into how such contexts are formed, as they focus primarily on uncovered code feedback without modeling dependency structures or object initialization processes.
We further observe that the required execution contexts are inherently encoded in the call chains leading to the focal method, together with the constructors of the involved classes. These call chains capture how objects are created, how external dependencies are invoked, and the order in which different components interact.
Therefore, we propose CAT, built on a dedicated static analysis framework that systematically captures relevant execution contexts. Specifically, CAT extracts call-chain information and associated initialization contexts, including caller-callee relationships, object constructions, and third-party dependencies, and explicitly provides the LLM with such rich project-level context, enabling it to generate valid tests even for methods with complex inter-module and third-party dependencies.
Using the same benchmark (Defects4J) as in its original experiments, PANTA is, on average, outperformed by CAT by 12.52, 12.97, and 14.39 percentage points (18.02%, 21.52%, and 26.94%) in line coverage, branch coverage, and mutation score, respectively. As discussed later in Section 4, CAT generates tests for each focal method individually, whereas PANTA generates tests once per focal class. As a result, CAT may incur higher overall generation costs due to its finer-grained generation process. Thus, we further perform a fairer comparison giving PANTA the same time budget as CAT, where the latter still achieves improvements of 8.94, 9.61, and 14.76 percentage points (12.23%, 15.11%, and 27.83% relative) in line coverage, branch coverage, and mutation score over the resulting time-bounded variant of PANTA. We also compare CAT against EvoSuite, a widely used search-based test generation tool that does not rely on an LLM. CAT outperforms EvoSuite by 9.67, 4.17, and 15.70 percentage points (13.37%, 6.04%, and 30.13% relative) in line coverage, branch coverage, and mutation score, respectively; however, EvoSuite attains higher branch coverage on five of the 14 projects.
To further assess the generalizability of our approach and increase the realism of our comparisons, we evaluate CAT on four additional Java projects collected from GitHub that were released after the employed LLM became publicly available, thereby making them unlikely to have been part of its training data. As discussed in Section 4.1.1, these projects are also more complex than those in Defects4J. On these unseen projects, CAT improves line coverage, branch coverage, and mutation score by 13.58, 12.02, and 24.64 percentage points (25.09%, 25.91%, and 94.37% relative), respectively, over the original PANTA, and by 7.80, 7.48, and 19.88 percentage points (13.02%, 14.68%, and 64.40%) over its time-bounded variant. Compared with EvoSuite, CAT improves the three metrics by 23.19, 14.16, and 17.30 percentage points (52.10%, 31.99%, and 51.72%), respectively.
These results suggest that explicitly modeling execution context, including call chains, constructor information, and third-party dependencies, substantially improves both the coverage and the fault-detection capability of LLM-generated tests in project-level test generation, also on previously unseen projects.
In summary, this paper makes the following contributions:
•
We identify a key limitation of existing path-guided project-level test generation approaches: uncovered execution paths alone are insufficient for constructing valid execution contexts in projects with complex inter-module and third-party dependencies. To address this, we introduce a context modeling strategy and provide a dedicated static analysis framework to systematically capture relevant execution contexts, including call chains, object constructors, and third-party dependencies.
•
Based on this strategy, we propose CAT, an LLM-based project-level test generation approach. To the best of our knowledge, CAT is the first approach to explicitly incorporate call-chain- and dependency-aware execution contexts into LLM-based project-level test generation, enabling effective test generation for complex software systems.
•
We conduct an extensive empirical evaluation on Defects4J and four newly released GitHub projects that are unseen by the employed LLM and exhibit higher complexity than Defects4J in terms of inter-class dependencies and project structure, demonstrating substantial improvements in line coverage, branch coverage, and mutation score over PANTA, the state-of-the-art LLM-based baseline, and over the search-based tool EvoSuite, and we release an open-source toolkit of CAT.
The remainder of this paper is organized as follows. Section 2 presents the motivating example for this paper. Section 3 presents the design of our approach CAT. Section 4 describes the experimental setup and reports the evaluation results. Section 5 reviews related work. Finally, Section 6 concludes the paper.
2. Motivating Example
In this section, we present a motivating example to illustrate the limitations of existing approaches in
handling focal classes with external dependencies.
The first two focal methods shown in Listing 1, hasXMLFormat and hasFormat, from the XmlFactory class in the JacksonXml-5f project of the Defects4J dataset, illustrate a common scenario in real-world codebases. Both their input type InputAccessor and return type MatchStrength are defined outside XmlFactory, introducing dependencies on external classes and requiring non-trivial object construction and cross-class interaction to correctly invoke these methods.
Such scenarios highlight a fundamental challenge for coverage-driven test generation approaches. Since these methods depend on externally defined types and initialization logic, simply guiding test generation toward uncovered code regions is insufficient. In particular, when the generation process is primarily driven by coverage feedback, it tends to focus on exploring new execution paths without explicitly reasoning about how required objects are constructed or how inter-class dependencies are resolved. As a result, the generated tests often fail to establish valid execution contexts for methods with complex dependencies, limiting their ability to reach and execute the target methods effectively.
In addition, focal classes often contain overloaded methods, such as multiple configure methods with different parameters (the last two methods as shown in Listing 1).
Method overloading is a common feature of real-world Java codebases, further complicating method-level test generation, as different overloads may require distinct input constraints and execution contexts.
Empirical evidence (Khan et al., 2024; Gil and Lenz, 2010) shows that method overloading is non-trivial in real-world Java code:
•
In a dataset of open-source Java repositories, more than 5% of method declarations are overloaded on average, with some repositories reaching 27% (Khan et al., 2024).
•
An earlier study (Gil and Lenz, 2010) found that over 14% of methods in a large Java corpus are overloaded.
Our approach addresses both limitations through a dedicated static analysis framework. First, we generate tests one focal method at a time, which avoids ambiguity caused by overloaded methods. Second, we systematically extract relevant execution contexts, including both call-chain information and external class dependencies, via static analysis (see Listings 2 and 3).
We illustrate our approach using the focal method hasFormat as an example.
Listing 2 shows the call-chain context of hasFormat in a simplified form. Each block gives the declaring class, the method with its parameter types and, after the arrow, its return type. For brevity, we list each indirect call chain from its public entry method up to the last method before the focal method; the final call to the focal method (which ends every chain) is omitted.
The first block is such an indirect chain. DataFormatDetector.findFormat(byte[]) wraps the given bytes in an InputAccessor and passes it to the private helper _findFormat, which calls hasFormat on the JsonFactory instances registered in the detector until one of them reports a sufficiently strong match. Since XmlFactory extends JsonFactory and overrides hasFormat, CHA links this call to the focal method, which is reached at run time when the detector holds an XmlFactory. The private helper cannot be called from a test and is removed by the visibility filter (Section 3.2.3); thus, findFormat is both the entry method and the last method before the focal method. The second block is the focal method itself, which, being public, can also be invoked directly.
Listing 3 shows the extracted dependency context. For each related class, we collect all public constructors. For abstract classes (e.g., InputAccessor), we further identify their concrete implementations. This information enables the LLM to construct valid object instances required for executing the focal method and its callers.
To improve coverage of the focal method, we prompt the LLM to generate tests that either directly invoke the focal method or indirectly invoke it through call-chain methods. This guidance helps the LLM construct diverse inputs and execution paths, thereby triggering more branches within the focal method.
For example, to indirectly invoke hasFormat via findFormat, additional dependencies—such as instantiating a DataFormatDetector object—must be satisfied.
