 outperform the baseline on the corresponding dataset, while a value below 0.5 suggests the opposite.
In addition, we applied the paired-sample Wilcoxon signed-rank test to line coverage, branch coverage, and mutation score to assess whether CAT’s observed improvements are statistically significant. We used a significance level of α=0.05\alpha=0.05. Therefore, a pp-value smaller than 0.05 indicates a statistically significant improvement.
4.1.3. Implementation
We implement the dedicated static analysis framework for call-chain extraction and dependency resolution described in Section 3.2 in Java, based on SootUp V2.0.0 (soot-oss, 2023), with approximately 1,200 lines of code.
For the evaluation pipeline, our implementation initially builds on PANTA (PANTA TestAutomation, 2025) and its associated scripts for the Defects4J experiments. However, to support the additional GitHub subjects, which commonly adopt multi-module Maven structures as discussed in Section 4.1.1, we substantially extend and refactor the original evaluation framework. In particular, we redesigned project parsing, built the orchestration, and implemented coverage-collection logic to correctly handle multiple modules and cross-module dependencies. Overall, our evaluation framework is therefore only partially based on PANTA and includes significant extensions to support realistic project-level settings.
Regarding the configuration of CAT, we set the maximum number of generation iterations Ng​e​nN_{gen} to 10 for all focal methods across all projects, as described in Section 4.1.2. We set the maximum call-path search depth dm​a​xd_{max} to 3 based on the same preliminary experiment. A larger depth substantially increases path-extraction cost, whose worst-case complexity grows exponentially with the average method out-degree and path length, leading to unacceptable analysis overhead, as discussed in Section 3.2. Finally, we set both mm and Nf​i​xN_{fix} to 3, following the default configuration of PANTA.
LLMs have rapidly evolved, encompassing both general-purpose models and those specifically tailored for code-related tasks. In this evaluation, we use Qwen3-Coder, which, when our work began, achieved state-of-the-art performance among open-source models on widely used code generation benchmarks, including SWE-Bench (Jimenez et al., 2023) and LiveCodeBench (Jain et al., 2024).
We deploy the Qwen3-Coder 30B model locally using Ollama (Ollama, 2025) with its default configuration. To ensure a fair comparison, we set the temperature to 0.2 and use JUnit 4 across all experimental settings on Defects4J, consistent with our baseline PANTA. We also use the same maximum output length of 16,384 tokens per LLM response for all LLM-based approaches, with no explicit limit on the number of tests generated per response. For the unseen projects, both PANTA and CAT use JUnit 5, following the Maven configurations specified in each project.
We conduct the evaluation on a Linux server equipped with a 56-core CPU, 125 GB of RAM, a single NVIDIA RTX 6000 Ada GPU, and running Ubuntu Linux 24.04.1 LTS.
Our tool and benchmarks can be found at: https://github.com/Amocy-Wang/CAT.

On average, CAT surpasses PANTAtb and PANTA by 8.94 and 12.52 pp (12.23% and 18.02%) in line coverage, and by 9.61 and 12.97 pp (15.11% and 21.52%) in branch coverage, respectively. Across most projects, CAT outperforms both baselines, highlighting the effectiveness of incorporating call-chain extraction for call context and dependency resolution for dependency context in prompts for project-level test generation. Two exceptions appear: JacksonXml, where CAT does not achieve the highest line coverage, and Codec, where the same holds for branch coverage.
Compared with EvoSuite, CAT achieves higher line coverage on all 14 projects, by 9.67 pp (13.37%) on average, whereas its average branch coverage is only 4.17 pp (6.04%) higher, with EvoSuite achieving the highest branch coverage on five projects (JacksonXml, JacksonCore, Jsoup, Time, and Lang). This is consistent with EvoSuite’s search, which directly targets individual branches as coverage goals.
For the JacksonXml project, CAT performs slightly worse than PANTAtb by 0.67 pp (1.03%) in line coverage, while achieving 4.20 pp (7.76%) higher branch coverage. This suggests that although the richer call-chain and dependency context provided by CAT is particularly effective for exploring diverse execution branches, the uncovered-path information used by PANTAtb still offers valuable guidance on input constraints and path-specific conditions, which can help cover certain lines of code. In other words, while CAT improves overall branch exploration by addressing dependency issues through call-chain graph information in the prompts, challenges related to precise input construction and oracle generation still remain. For example, many failures stem from expected values that do not match the current implementation’s output and from incorrectly generated inputs.
For the Codec project, CAT achieves higher line coverage than PANTAtb but slightly lower branch coverage. In particular, CAT improves line coverage by 3.99 pp (4.85%), while reducing branch coverage by 3.99 pp (4.91%) compared to PANTAtb. This result reflects the characteristics of the Codec project and the different mechanisms of the two approaches. Compared to other subjects, Codec contains a higher proportion of branch-intensive, rule-based logic, where execution paths are heavily determined by fine-grained input conditions. In such a setting, CAT benefits from call-chain-guided execution context construction, which helps resolve cross-class dependencies and improves reachability of executable code, leading to higher line coverage.
However, this mechanism tends to favor structurally guided execution paths, which may not sufficiently explore rare or highly conditional branches. In contrast, PANTAtb leverages uncovered-path feedback at the class level, which can better guide the exploration of less frequently exercised execution paths, thereby achieving slightly higher branch coverage.
This effect is also evident at the class level. For example, in the DoubleMetaphone class, PANTAtb achieves 69.96% line coverage and 57.53% branch coverage, whereas CAT achieves 75.96% line coverage and 57.08% branch coverage. While CAT improves line coverage by 6.00 pp (8.58%), it slightly decreases branch coverage by 0.45 pp (0.78%).
These observations naturally raise the question of whether combining the complementary strengths of both approaches could further improve performance. Specifically, we investigate whether integrating uncovered-path information from PANTA with the call-chain and dependency context from CAT yields additional gains. To answer this question, we conduct experiments on the Defects4J projects by augmenting CAT’s prompts with the uncovered-path information from PANTA, resulting in the variant CATpath introduced in Section 4.1.2.
However, our results show that this combination does not consistently improve performance across projects. The detailed results (included in the replication package) show that CATpath achieves 71.30% line coverage and 63.35% branch coverage, while CAT still outperforms it by 10.71 and 9.88 pp (15.02% and 15.60%), respectively. One possible explanation is that including uncovered-path information substantially increases prompt length. In particular, in early iterations where branch coverage is still low, a large number of uncovered branches are included in the prompt. For branch-intensive focal methods, this can lead to prompt length increases of up to approximately 2×–3× compared to CAT alone. This enlarged prompt may dilute or overshadow critical call-chain and dependency signals, ultimately leading to suboptimal prompt effectiveness. We leave the exploration of more effective strategies for integrating these two complementary sources of information to future work.
Although our work primarily focuses on improving code coverage, higher coverage is ultimately expected to enhance the defect-detection effectiveness of the generated tests. Therefore, to provide a more comprehensive evaluation of CAT, we additionally report the mutation scores achieved by CAT, PANTAtb, PANTA, and EvoSuite in Table 3. On average, CAT achieves a mutation score of 67.80%, outperforming PANTAtb (53.04%), PANTA (53.41%), and EvoSuite (52.10%) by 14.76, 14.39, and 15.70 pp (27.83%, 26.94%, and 30.13%), respectively. These results show that CAT detects faults more effectively and highlight the benefits of incorporating call-chain and dependency contexts into LLM-based project-level test generation.

Cost and generated tests. Table 5 reports the LLM tokens consumed, the generation time, and the tests retained by the three LLM-based approaches on Defects4J. The time includes generation, repair, compilation, and execution; we report the one-time static analysis of CAT separately in Section 4.1.2 (8.35 hours total, 2.4% of its generation time). Summed over all projects, CAT consumes 154.9 million tokens and 353.8 hours (about 51K tokens and 7.1 minutes per focal method, or 2.72 hours per focal class), 2.09 and 2.99 times as much as PANTA (74.1 million tokens and 118.5 hours), because it runs the generation-and-validation loop for each focal method rather than once per class. Across both datasets, CAT runs, per focal method, an average of 5 of the maximum Ng​e​n=10N_{gen}=10 generation iterations and 2 repair attempts (i.e., 7 LLM calls). LLM inference accounts for 27.16% of the generation time, and compilation and test execution account for the rest. PANTAtb, which runs for the same time as CAT, consumes 228.8 million tokens and retains 18,405 tests (851 per project), 44.9% more than CAT (12,702; 650 per project) and 65.9% more than PANTA (11,092; 549 per project); it retains more tests than CAT on 9 of the 14 projects. Yet CAT achieves 8.94, 9.61, and 14.76 pp (12.23%, 15.11%, and 27.83%) higher line coverage, branch coverage, and mutation score (Table 3). Moreover, with these additional tests, PANTAtb improves line coverage over PANTA by only 3.58 pp (5.15%) and does not improve the mutation score (53.04% vs. 53.41%). The improvements of CAT are therefore unlikely to stem from the number of retained tests. Mocking frameworks are rarely used: in 0.0% of the retained tests of CAT in every project except JacksonXml (2.9%), and in at most 2.2% of those of PANTAtb and PANTA in any project, so the tests of all three approaches rarely rely on a mocking framework.
In practice, when running CAT, the cost amounts to about 7.1 minutes and 51K tokens per focal method on our single-GPU server (Section 4.1.3). Since test generation is typically performed offline rather than interactively, we consider this cost acceptable, in particular because it cannot be substituted by running PANTA longer: with the same time budget, PANTAtb still achieves 8.94, 9.61, and 14.76 pp lower line coverage, branch coverage, and mutation score than CAT. The cost can also be reduced in practice: generation already stops early when coverage stagnates, most of the time is spent on compiling and executing tests rather than on LLM inference, and focal classes are processed independently and can thus be handled in parallel. Developers may also apply CAT selectively, e.g., to the focal methods that a cheaper tool such as EvoSuite leaves uncovered.
Hallucinations in the generated tests. On Defects4J, we observed two main types of hallucinations in the tests generated by CAT. API hallucinations affected 13.8% of all generated tests and involved references to nonexistent program elements or invalid uses of existing ones: accessing private or protected members (3.6%), referencing nonexistent methods, fields, or constants (3.3%), importing an existing class from the wrong package (2.9%), invoking methods with incompatible argument types, mostly involving overloaded methods (1.9%), misusing abstract classes or interfaces, e.g., by attempting to override a method that does not exist in the supertype (1.4%), and referencing nonexistent classes or test helpers (0.7%). Oracle hallucinations affected 9.0% of all generated tests and involved expected outcomes inconsistent with the program’s observed behavior: incorrect asserted values or conditions (8.8%) or expected exceptions that were not thrown (0.2%). The remaining failures involved type mismatches, unhandled checked exceptions, runtime exceptions caused by invalid inputs or object states, and malformed output.
RQ1 Summary
On Defects4J, CAT achieves the highest average line coverage, branch coverage, and mutation score among all approaches. Compared with PANTAtb, PANTA, and EvoSuite, it improves line coverage by 8.94, 12.52, and 9.67 pp (12.23%, 18.02%, and 13.37%), branch coverage by 9.61, 12.97, and 4.17 pp (15.11%, 21.52%, and 6.04%), and mutation score by 14.76, 14.39, and 15.70 pp (27.83%, 26.94%, and 30.13%), respectively, showing that the call-chain and dependency contexts improve both test coverage and fault-detection capability. These gains come at about three times the generation time and twice the tokens of PANTA. However, PANTAtb, which runs as long as CAT and uses more tokens while retaining more tests, still achieves lower coverage. At the same time, 13.8% (API hallucinations) and 9.0% (oracle hallucinations) of the tests generated on Defects4J initially fail because of hallucinations and must be repaired or discarded. Moreover, naively combining uncovered-path information with call-chain and dependency contexts does not lead to further improvements, suggesting that effectively integrating heterogeneous sources of information remains a significant challenge.
