3. Approach
In this section, we introduce CAT, a Call-chain-Aware Test-generation approach. Section 3.1 presents an overview of our approach, describing its iterative workflow consisting of a generation phase and a fixing phase, along with the prompts used in each phase. Section 3.2 presents the dedicated static analysis framework, detailing the algorithms for systematically extracting call-chain information and resolving dependency contexts to construct relevant execution contexts for test generation. Section 3.3 describes the prompt design for the generation phase, which integrates the contexts extracted in Section 3.2. Section 3.4 describes the prompt design for the fixing phase.
3.1. Overview
CAT consists of two phases: a generation phase and a fixing phase. It can operate with or without existing tests. When a test class already exists, CAT preserves the existing tests and inserts each newly generated test into the same class. A new test is retained only if the class still compiles and the new test passes. In this setting, the stopping criterion is initialized with the code coverage achieved by the existing tests. When no tests are available, CAT first creates a pseudo test file with placeholder test functions, ensuring that newly generated tests can be compiled and executed within a valid test harness.
As illustrated in Figure 1, CAT follows an iterative workflow that alternates between these two phases. In the generation phase, CAT first statically extracts call-chain and dependency information for the method under test (MUT), which it performs only once before the iterative generation process. The extracted call-chain and dependency contexts, along with the source code of related classes, are incorporated into the generation prompt to guide test generation for candidate tests. Based on this prompt, CAT iteratively generates tests to maximize coverage. Section 3.3 presents details of this phase.
In the fixing phase, CAT repairs failing tests by leveraging execution feedback. Specifically, failed tests and their corresponding error messages are incorporated into the fixing prompt, allowing up to Nf​i​xN_{fix} repair attempts within each generation iteration. Section 3.4 presents details of this phase.
The workflow continues until the testing effort becomes ineffective, i.e., when neither line nor branch coverage improves for mm consecutive iterations, or until the maximum number of generation iterations Ng​e​nN_{gen} is reached, at which point the process terminates.
Figure 1. Overview of the CAT workflow
CAT generates regression tests: the current implementation serves as the reference for expected behavior. Assertions capture the values observed during execution, and the fixing phase updates failing assertions to match the observed behavior without modifying production code. A passing test therefore documents current behavior and flags future changes, but it does not establish that the behavior is correct. The same assumption underlies EvoSuite’s regression assertions (Fraser and Arcuri, 2011) and the tests retained by PANTA (Gu et al., 2025).
We do not present the full generation and fixing prompts in the paper because they are too long to include in the main text. Instead, detailed prompt templates are provided in the replication package. Nevertheless, as illustrated in the overview and further elaborated in the following sections, the generation prompt is carefully designed to incorporate extracted call-chain and dependency information. Next, we describe how we obtain these key components and integrate them into the prompt.

3.2. Call Chain Extraction and Dependency Resolution
CAT is built on a dedicated static analysis framework that systematically captures relevant execution contexts for test generation. Specifically, it performs static analysis to identify potential invocation paths from accessible entry points to the target method and extracts call-chain information along these paths. It also analyzes class and method metadata to determine initialization requirements and related dependencies, including object constructors and third-party dependencies, thereby constructing executable, semantically valid contexts for test generation.
As outlined in Algorithms 1, 2, and 3, this process consists of three main steps. First, we construct a call graph and collect relevant program metadata based on a Class Hierarchy Analysis (CHA (Dean et al., 1995)) (Algorithm 1). Next, we extract all invocation paths that can reach the target method under a bounded depth (Algorithm 2).
Finally, we refine the extracted call paths to retain only feasible entry points for test generation, since some methods may not be publicly accessible or may belong to non-public or abstract classes that cannot be directly invoked in generated tests. Based on these filtered paths, we infer the set of classes that require initialization, along with their associated initialization methods, to ensure the generated tests can construct the necessary execution context (Algorithm 3).
We then incorporate the filtered call-chain paths and dependency information into the generation prompt to guide the test generation process, as described in Section 3.1.
3.2.1. Call Graph Construction and Metadata Collection
As shown in Algorithm 1, we first construct a call graph and collect metadata about classes and methods. Given the classpath C​PCP, a target class CtC_{t}, and a target method name mtm_{t}, the procedure consists of three phases.
In the first phase, we load all bytecode from the classpath and extract the set of classes 𝒞\mathcal{C} (lines 1–3). This phase establishes the scope of the global analysis required for subsequent call graph construction.
In the second phase, we collect a set of metadata maps, including the class visibility map classVis, the method visibility map methodVis, the constructor map ctors, and the implementation map impls. The visibility maps record whether each class or method is publicly accessible, which is essential for identifying valid invocation entry points and feasible call paths. The constructor map stores public constructors for each class, enabling object instantiation during test generation. The implementation map maps supertypes (including superclasses and interfaces) to their public concrete implementations, facilitating the resolution of virtual and interface dispatch during call graph construction.
In the third phase, we adopt Class Hierarchy Analysis (CHA) (Dean et al., 1995) to construct the call graph C​GCG, as it provides a favorable balance between scalability and recall. Since the goal of CAT is to provide the LLM with candidate invocation paths that may reach the target method, we prioritize broad coverage of potential call relationships over aggressive pruning of infeasible edges. Compared with more precise yet computationally expensive alternatives, such as RTA (Bacon and Sweeney, 1996) or points-to-based analyses (Smaragdakis and Balatsouras, 2015), CHA enables lightweight whole-project analysis without requiring complete entry-point information, making it particularly suitable for project-level iterative test generation.
For CHA construction, we use as the root set ℛ\mathcal{R} (line 19) only the public methods of all classes on the classpath (i.e., from the project and its libraries), rather than all methods. This choice matches the practical test-generation setting, where only externally accessible methods can serve as entry points. It also reduces spurious call paths that start from private helpers, improving both the relevance and scalability of the extracted call chains. Note that ℛ\mathcal{R} only determines where CHA starts: from a public entry point, CHA still traverses non-public callees, so a non-public focal method can be reached through the public methods that call it (directly or via non-public helpers).
Because the generated test class is placed in the focal class’s package, package-private and protected methods in that package could also be used as entry points. We nevertheless restrict ℛ\mathcal{R} to public methods to stay consistent with our filtered call paths and initialization context (which include only public members) and to limit the cost of path enumeration, since each additional entry point adds a starting node and the enumeration cost grows exponentially with path length. We discuss this restriction as a threat to validity.
As discussed in Section 2, a single method name may correspond to multiple overloads with different parameter lists. To ensure coverage of all potential invocation paths to the target method, we collect all methods in CtC_{t} whose names match mtm_{t} as the target method set 𝒯\mathcal{T} (line 21).
The outputs of this step include the call graph C​GCG, the metadata maps (classVis, methodVis, ctors, and impls), the root set ℛ\mathcal{R}, and the target method set 𝒯\mathcal{T}.

3.2.2. Depth-Limited Call Path Extraction
After constructing the call graph and collecting metadata, we extract candidate call paths from entry points to target methods. Given the call graph C​GCG, the set of entry points ℛ\mathcal{R}, the set of target methods 𝒯\mathcal{T}, and a maximum search depth dm​a​xd_{max}, we perform a depth-limited depth-first search (DFS) to enumerate all feasible call sequences, as shown in Algorithm 2.
The extraction procedure consists of three phases. First, we construct a forward adjacency map FF from C​GCG to support efficient traversal (lines 1–5). Second, we perform a backward reachability analysis to identify methods that can potentially reach any target method, pruning unreachable nodes and thereby reducing the search space for path enumeration (lines 6–14). Finally, we initiate a depth-limited DFS from each reachable entry point, enumerating all paths that lead to target methods while respecting the maximum depth constraint (lines 15–19). The DFS maintains a stack SS for the current path and a visited set to prevent cycles; whenever a target method is reached within the depth limit, the current path is added to the set of raw call paths 𝒫\mathcal{P}.
The maximum search depth dm​a​xd_{max} is introduced to prevent the DFS from exploring exponentially many paths in large projects. Without this limit, the worst-case complexity grows roughly as O⁡(koutd)O(k_{\text{out}}^{d}), where koutk_{\text{out}} is the average out-degree of a method and dd is the path length, which is computationally infeasible for project-level analysis (Dean et al., 1995; Horwitz et al., 1990). Importantly, we do not perform extraction and dependency resolution (discussed later) at each generation; instead, we run them once at the beginning as a preprocessing step and reuse the results throughout the process.
The resulting set 𝒫\mathcal{P} contains all potential sequences of method invocations from entry points to target methods within the depth bound. These paths may include methods that are not publicly accessible or belong to non-public classes, which are infeasible for test generation. We therefore perform a filtering and initialization inference step in the next phase, as described in Section 3.2.3.
