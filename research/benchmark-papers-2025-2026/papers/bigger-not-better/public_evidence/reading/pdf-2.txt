-processing projects. The selection was constrained by the
       block-level repair setting used in this study: a bug was included only if the buggy code could
       be localized to a function or class, the relevant block could be extracted for prompting, and the
       associated test suite could be executed in our environment. Bugs requiring multi-file repairs,
       repository-level changes, unavailable dependencies, or non-reproducible test environments
       were excluded.
           We evaluate six open-source code-oriented LLMs ranging from 1.5B to 15B parameters.
       Models were selected based on open-source availability, Python support, and prior use or
       performance in code-related benchmarks such as HumanEval [5] and CodeXGLUE [13].
       Following prior work [2], we categorize models up to approximately 6–7B parameters as
       small and models from 7B to 15B parameters as medium-sized. Table 1 summarizes the
       selected models and their parameter sizes. All selected models are publicly available on the
       Hugging Face1 model repository. All models were executed locally on the same hardware.
       Proprietary API-based models were not included because their inference energy cannot be
       measured directly under the same hardware and measurement conditions.




       3.4     Prompting and Execution

       A fixed zero-shot prompt was used for all models and tasks to ensure a consistent evaluation
       setting. We deliberately used a single standardized prompt rather than model-specific
       prompting or alternative prompting strategies, such as few-shot prompting. This design
       reduces prompt engineering as a source of variation and enables the models to be compared
       under identical prompting conditions [4] [3]. The prompt instructs the model to generate a
       complete Python function or class and to output only executable code.

    Generated outputs were evaluated without manual intervention. Outputs containing
non-code text, Markdown formatting, incomplete blocks, syntax errors, unexpected function
or class structures, or missing return statements were counted as unsuccessful repairs (counted
as failures in Pass@k). We intentionally did not edit, clean, or reformat generated outputs
because adherence to the fixed output constraints is part of the evaluated zero-shot repair
setting. For executable repairs, correctness was determined solely by whether the generated
repair passed the associated bug-specific test suite.
    All models used the same prompt template and were executed without task-specific
or model-specific decoding tuning. Generation followed the defaults of the inference lib-
rary/model configuration used in our scripts. The batch size was 1. Model loading time
was excluded from inference-time and energy measurements. Random seeds were not fixed;
instead, each bug-model pair was executed 10 times to capture output and measurement
variability.
    For each bug-model pair, we perform 10 independent runs, resulting in 2,400 intended
model executions. Each run takes a project identifier, bug identifier, and model identifier
as input; prepares the BugsInPy workspace; extracts the buggy block; runs LLM inference;
inserts the generated repair; executes the bug-specific tests using pytest; and records
correctness, inference time, and GPU energy.
    A run is successful if the generated repair passes all bug-specific tests. A bug is considered
fixed by a model if at least one of the model’s 10 generated repairs passes the tests. Runs
failing due to syntax errors, runtime errors, failed tests, invalid output format, or timeout
are counted as unsuccessful. The timeout policy was governed by the overall SLURM job
time limit.
    All experiments are conducted on a dedicated GPU node equipped with an NVIDIA
Tesla V100 GPU with 32 GB memory, 4 CPU cores, and 128 GB RAM. Each experiment
is executed as an independent job with an identical configuration, and a fixed delay is
introduced between repeated runs to reduce thermal effects.
    All runs used the same software environment, model execution scripts, and measurement
scripts. The models were loaded before each measured run. Model-loading energy and time
are excluded from the reported inference cost.

           Because NVML reports GPU-side power, the reported values represent GPU inference
       energy rather than full-system energy. Baseline idle GPU energy was measured under the
       same job configuration and sampling interval, and subtracted from measured inference energy
       to estimate the additional GPU energy associated with repair generation.
           For each run, we record the model identifier, bug identifier, execution status, number of
       tests passed, total number of tests, correctness outcome, inference time in seconds, and GPU
       energy in Joules.
           The collected data are aggregated across repeated runs. For RQ1, we analyze Pass@1, the
       number of bugs fixed, and inference time. For RQ2, we analyze GPU energy consumption.
       For RQ3, we jointly compare repair correctness, inference time, and GPU energy consumption
       to identify correctness-energy trade-offs across models.
           To compare energy differences between models, we aggregate inference-energy measure-
       ments per bug-model pair across the 10 runs and use the per-bug average as the unit of
       analysis. This gives one paired energy value per bug for each model. We use the Wilcoxon
       signed-rank test [14] for pairwise comparisons and report Vargha–Delaney A12 effect sizes [10]
       to quantify the magnitude of differences. Because multiple comparisons are performed,
       p-values are interpreted together with effect sizes and descriptive trends rather than as the
       sole basis for conclusions.
           Finally, we conduct an exploratory inspection of generated repairs that failed to fix the
       observed failure to identify recurring failure patterns, such as invalid syntax, incomplete
       repairs, incorrect function or class structure, incorrect repair logic, or outputs that do not
       address the observed failure. This inspection supports the interpretation of the quantitative
       results rather than producing a validated taxonomy.

        Taxonomy of Recurring Failures. Across all 20 manually inspected bugs, failures fall into
        three main categories:
        1. Structural & Format Violations (∼50% of failures in medium models): Inclusion
           of Markdown tags, explanatory text, duplicated function signatures, or code outside the
           target block.
        2. Incomplete Repairs (∼30% of failures): Correct handling of primary branches but

           invalid state checks, or incorrect enumeration (enum) indexing (e.g., in Black 3 ).

        violations were more common than complex algorithmic misunderstandings (such as incorrect
        recursion or invalid mathematical operations). In several cases, generated outputs partially
        captured the intended repair logic but failed because they violated the required block structure
        or output format. This suggests that within the evaluated zero-shot block-repair setting,
        output compliance can be as important as the quality of semantic repair.
