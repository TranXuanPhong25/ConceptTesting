# Prompt provenance gate for ConceptCoder-to-test-generation work

The anchor paper is [ConceptCoder](https://arxiv.org/html/2603.23470). Its Appendix A.4, Listing 1 publishes a **hierarchical prompt for vulnerability classification**: inspect named vulnerability concepts, then output `@@VULNERABLE@@` or `@@NOT VULNERABLE@@`. It does not publish a prompt that generates test inputs. The paper's principal method is concept-supervised fine-tuning, not this prompt. Therefore a prompt that asks for tests cannot honestly be described as the unchanged "original ConceptCoder prompt."

The test-generation baseline used in our earlier pilot is instead the [TrickCatcher artifact](https://github.com/RinCloud/TrickCatcher), pinned at `a0d285a77efff7c93fc280d606497d9de5e1defe`: `Datasets/EvalPlus/PromptTemplates/geninput_direct_sys` (SHA-256 `b1b5f38811222eef6b0b6e1d5badd39248f48f09cb085648a7f441dae495e902`) and `geninput_usr` (SHA-256 `ce7b4adbf8d6c00a4f855191256c76ef7bf7dbad18362a8e0f73b1d3e3129317`). Our baseline passed these templates unchanged. The generic and concept arms **appended new text to the user message**, so their complete prompts were not original paper prompts. The custom three-field cards and Python AST concepts were not ConceptCoder labels.

Before any further run, record for each arm: exact source paper and artifact revision; verbatim prompt file and hash; all substitutions and additions; source of concept names and labels; model settings; and whether the arm is an exact reproduction or an extension. Do not call a ConceptCoder-derived test-generation arm an exact original-prompt run. If the required constraint is literally "unchanged ConceptCoder Listing 1 for every arm," stop: its specified output is a vulnerability label, not a test case. An adaptation to test generation requires a separately named prompt extension and user agreement on the baseline protocol.

## Audit after the prompt-provenance requirement (2026-09-25)

- The TrickCatcher pilot now rejects a changed `geninput_direct_sys` or `geninput_usr` by SHA-256 before contacting Gemini. Each new JSONL row records the paper baseline, template hashes and whether the complete prompt is `verbatim_original` or a `concept_or_plan_extension`. This safeguard is forward-looking; older generated JSONL does not contain these new fields.
- The local Magma C pilot has a useful canary oracle and 100 stored bug items, but its `magma/prompts.py` prompts are **project-authored**, not original Magma or ConceptCoder test-generation prompts. Its earlier statistics must not be presented as a prompt-faithful development of either paper. `magma/RESULTS.md` also flags patch-derived fault-condition leakage and later feedback leakage in older comparisons. Do not reuse their positive counts as clean concept evidence.
- The local C annotation is an eight-label tree-sitter reimplementation (seven ConceptCoder VD-like labels plus `if_statement`). `conceptcoder_bridge/paper_labels.py` projects it to the **seven published Table 1 names**, dropping the extra label and reading only source-local fields. On the 100 stored Magma items, 93 have at least one projected label. This is still **not the authors' official analyzer**; no agreement/accuracy against it has been measured.
- The ConceptCoder paper's figshare page advertises a 132.45 MB code/data package, but its download endpoint returned an AWS WAF challenge from this environment on 2026-09-25. We have not acquired or executed the official labeler. The seven-label bridge is therefore preparation, not a reproduced ConceptCoder annotation.

Decision gate: do not run another Gemini comparison under a "ConceptCoder" heading until (1) a compatible C/C++ test-generation paper's original prompt is sourced and pinned, (2) the seven-label source is explicitly identified as official or reimplemented, and (3) all arms receive identical non-concept context and a non-leaky bug oracle. If the official ConceptCoder package becomes accessible, compare labeler agreement first.
