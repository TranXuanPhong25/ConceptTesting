## 1. Step a: defensible hypothesis enumeration, overstated localization interpretation

1. **The implementation substantially follows the amended plan.** It enumerates mutmut edits, maps them to four site/type families, retains public-input survivors, generates templates, and groups by `(line, type)`. Ranking is descending distinguished-survivor count, descending survivor count, type priority, then line; selection uses distinct lines. The ordinary site selection is at most three concepts with two inputs each, with a separate MISSING_CASE fill. Neither CFG nor a reference enters this ranking. (`L/PLAN_FAULT_TEMPLATES.md:13–27,57–60`; `V31/ft_run.py:80–149`; `V31/ft_concepts.py:34–62,283–335`.)

2. **“Path condition” is too strong a description here.** `site_constants` collects integer literals on the mutation's source line plus 0 and 1. Constants from all surviving BOUNDARY sites are pooled, sorted and capped at eight before template generation. There is no enclosing-guard conjunction, backward substitution through assignments, loop constraint or site-specific feasibility solve. Templates change one public example at one argument/element position; ranking can use inputs labelled with any template type. This is a literal-guided neighbourhood, not path-condition-directed generation. (`V31/ft_concepts.py:52–62,244–271,293–315`; `V31/ft_run.py:113–125`.)

3. **This is not Metallaxis/MUSE-style suspiciousness.** Standard MBFL uses how mutations affect passing versus failing tests. The collected FlexFL background explicitly describes this contrast and identifies Metallaxis and MUSE as different scoring/aggregation schemes. V31 has no failing-test labels at selection time: it measures behavioural alternatives left unresolved by public examples. That is a reasonable test-adequacy hypothesis, but does not supply the failure-associated evidence of standard MBFL. (FlexFL, §II-A, locally `B/papers/flexfl-flexible-and-effective-fault-localization-with-open-source-large-lan-1c4a806c/public_evidence/paper_fulltext.txt:160–167`; `V31/ft_concepts.py:283–299`.)

4. **Competent-programmer/coupling assumptions do not make each survivor a plausible correct fix.** Being near correct code motivates small mutation operators; coupling motivates tests that kill simple mutants also detecting more complex faults. Neither implication reverses into “a mutant of an already buggy PUT is correct because it passes these few examples.” A survivor may be another wrong implementation, unreachable under the examples, or equivalent to the PUT. The collected MUTGEN audit explicitly assumes original-code correctness; AdverTest likewise generates on fixed reference versions. Their results cannot establish this reverse repair interpretation. (`research/mutgen/ORACLE_PROTOCOL.md:7–19`; AdverTest, §6 “Reference-Version Test Generation”, locally `B/audit/RECOMMENDATIONS.md:80–86`; `V31/ft_run.py:3–9`.)

5. **The v35 criterion is valid as a partial-correction witness, not as ground-truth localization.** For a valid exposing input (x), `M(x)=R(x) != PUT(x)` proves that this edit corrects the observed outcome at (x). It does not prove that the edited line caused the original defect, that the fault type is right, or that the mutant is a correct program. A change elsewhere can mask or compensate for an error. The collected FLIMs paper explicitly describes reachability bypass, state cancellation and propagation interference producing such coincidental correctness, including the risk to MUSE's fail-to-pass interpretation. (`L/analysis/v35_concept_ceiling/ceiling.py:44–67`; FLIMs, §IV-C2–C3, locally `B/papers/flims-fault-localization-interference-mutants-definition-recognition-and-mi-7d0c3782/public_evidence/paper_fulltext.txt:350–361`.)

6. **14/17 is conditional and existential.** The 16 tasks with no exposing pool input cannot be assessed by this definition; they are not evidence against single-edit representability. On the other 17, success requires only one of many surviving mutants to match on one exposing input. Different mutants can match different inputs. V35 deduplicates successful lines and counts each task once, so multiple survivors do not literally multiply the task numerator; they do increase opportunities for accidental matches and for a selected line to count as a hit. Task 132 has nine matching lines; task 163 has sixteen. Hit scoring checks line only, not `(line, type)` or the particular alternative shown. (`L/analysis/v35_concept_ceiling/ceiling.py:51–67`; `C/ceiling.json:329–347,371–397`.)

7. **Equivalent mutants have two distinct roles.** A mutant truly equivalent to the PUT cannot match the reference on an input where the PUT differs. Therefore it cannot directly inflate the locating numerator. Finite public-test survival is not semantic equivalence, however, and indistinguishable/equivalent survivors can inflate the ranking's secondary survivor count. The code does not collapse mutants into behavioural equivalence/subsumption classes. This explains a possible ranking bias, not a measured equivalent-mutant prevalence. (`V31/ft_run.py:104–113`; `V31/ft_concepts.py:289–299`; `L/analysis/v35_concept_ceiling/ceiling.py:44–59`.)

The stronger four-task result has a concrete counterexample to the repair interpretation: task 36's two strict mutants `m70` and `m81` correct all eight exposing inputs, but on pool input index 9 the PUT/reference return 2 while both mutants return 0. This is a regression on an input the original handled correctly. The analogous strict-but-regressing tasks are 56, 101 and 163. These observations diagnose existing candidates; they are not proposals for new VibePass tests. (`A/cases/36/tool/phase2/result.json:1`; `C/reference/9ed8aed98083144f86f1330cac25d556ff1c69b7e02dd1effec067a6a6c8c48f/result.json:1`; corresponding regression evidence in §5.)

**How much is outside single-edit mutation? Not identifiable from these artifacts.** Three pool-exposed tasks—103, 161, 171—have no partial-correcting survivor in the enumerated set; another 16 have no exposing pool input. Thus 3/17 is a measured failure of this operator set on observed discrepancies, not a rate of intrinsically multi-line bugs. Even the 14 successes do not establish correct single-edit repairs. There are no minimal-patch/fault-type ground-truth labels in this ceiling protocol. A defensible report is “14 partial corrections, 8 all-exposing corrections, 4 regression-free finite-pool corrections; true non-single-edit prevalence unknown,” not “most VibePass bugs are/are not single-edit.” (`C/ceiling.json:279–288,360–369,425–435`; `L/analysis/v35_concept_ceiling/PREREG.md:12–25`; §5 audit.)

**MISSING_CASE is an input-template label, not a measured defect class.** There is no insertion of a missing case or algorithm in the mutant catalogue: its site is `None` and it is filled from degenerate-input templates. A missing branch, multi-line dependency or specification misunderstanding can lack any enumerated correct edit. Conversely, a bug informally described as a missing case might still be compensated for by a simple mutation. Counting MISSING_CASE-labelled inputs cannot estimate either prevalence. (`V31/ft_concepts.py:11–17,177–187,330–335`; `V31/v4_tools.py:36–78`.)

**The registered stop remains valid; its broad explanation does not.** V35 mechanically applies `14 < 17`. But its ceiling cannot exceed pool coverage, so a pool exposing fewer than 17 tasks would force stop regardless of mutant quality. The rule conflates reaching exposing inputs with repair representability. Retain the stop for this frozen direction and its numbers; do not treat it as a general refutation of mutant localization. Likewise, absence of an exposing concept input does not prove the site/type hypothesis wrong, despite the stronger wording in v34's post-hoc discussion. (`L/analysis/v35_concept_ceiling/PREREG.md:23–28`; `L/analysis/v35_concept_ceiling/ceiling.py:71`; `L/analysis/v34_ftplacebo_results.md:40–48`.)

## 3. Ranking and implementation findings

- **Ranking is sensible for finding behavioural uncertainty, weakly grounded for finding faults.** A high distinguished count means templates expose more unresolved alternatives. It does not measure spec violation, correction without regressions, or likelihood of a real fault. **Hypothesis:** mutation-rich lines and easy-to-perturb outputs outrank sparse but semantically wrong logic; raw counts and survivor ties reinforce this. No failure labels or semantic evidence counterbalance that effect. (`V31/ft_concepts.py:283–299`.)
- **The pool and selection weaken type specificity.** All template types can distinguish a group's mutants; matching type is only a late input tie-breaker. Global deduplication labels degenerate inputs MISSING_CASE first. Actual concept/template matches were only 62/143. **Hypothesis:** substantial cross-type overlap makes site/type labels less informative. (`V31/ft_concepts.py:252–270,311–327`; `L/analysis/v31_faulttemplate_results.md:28–30`.)
- **11 versus 9 is weak evidence, not proof of random ranking.** This compares selected inputs with one seeded random sample from the same normal-return pool, not random site rankings; total selected-input counts can differ. The full pool exposes 17 tasks, so selection discards available exposure, but this comparison does not identify an optimal ranking or establish statistical equivalence to random. (`V31/ft_run.py:135–147`; `L/analysis/v31_faulttemplate_results.md:13–14,28`; `C/ceiling.json:4`.)
- **Domain filtering is an empirical prior, not input validity.** It forbids shorter sequences and new character classes, and infers positive/nonnegative integer bounds from public examples. Valid unseen classes can therefore be removed, while invalid combinations remain. This is a plausible pool bottleneck, not a measured attribution to particular VibePass defects. The registered pilot20 check itself fell from 8 to 4 exposure tasks after this filter; selected VibePass templates still included 31 contract-invalid inputs. (`V31/ft_concepts.py:205–240`; `V31/PREREG.md:1207–1222`; `L/analysis/v31_faulttemplate_results.md:13,29`.)
- **A real specification mismatch: the cap is on site concepts, not all concepts.** MISSING_CASE is appended after site selection, without rechecking the concept cap or its two-input limit. Ten frozen tasks have four concepts; task 36 shows three site entries followed by MISSING_CASE. This qualifies “≤3 concepts ×2 inputs”; total inputs remain capped at six. It does not change v35's site-only hit counts. (`V31/ft_concepts.py:303–335`; `A/cases/36/tool.json:120–256`; `L/analysis/v35_concept_ceiling/ceiling.py:60–66`.)
- **Latent survivor-filter issue, inactive here.** The code compares only public inputs where the PUT returned `ok`/`exception`; it can ignore PUT timeouts/skips instead of enforcing agreement on every public input. Cached phase1 PUT outcomes are normal on all 94 public executions, so this issue does not explain these results. The 200-survivor cap also cut no survivor in these 33 tasks. These are audited artifact facts, not assurances for other cohorts. (`V31/ft_run.py:104–113`; phase1 audit in §5.)
- **No arithmetic/timeout bug found that overturns the reported stop.** All 305 entries in v34's generation freeze, current protocol source hashes and evaluator-file hashes matched. Cached recomputation matches v35; no mutant/phase error was recorded in these tool summaries. However, v35 itself does not verify those hashes, and the generation manifest excludes the raw `/tool/` files it later reads. This is a provenance limitation, not evidence of altered data. The typed comparison also differs from the tool's raw-repr comparison, so they should not be described as identical semantics. (`V34/ft_run.py:328–329`; `L/analysis/v35_concept_ceiling/ceiling.py:31–59`; `V34/flow_run.py:399–441`; `V31/ft_concepts.py:276–280`; audit §5.)

### Top five by fit to constructing revealing inputs at a candidate site

Ranking is this review's **mechanism-fit judgment**, with platform/oracle limits included; it is not a prediction that any paper will solve the eight tasks. CPU gates below are proposed desk/cached-data checks only, not executed paper reproductions or requests to build Python ports.

**1. UnitCon: Synthesizing Targeted Unit Tests for Java Runtime Exceptions — FSE / PACMSE, 2025.** Step b constructs API-call sequences using error preconditions, method summaries, semantic redundancy pruning and backward/forward search prioritization. Step a can obtain candidate sites from Infer alarms rather than failing tests. This is genuinely different from v31's single public-example edit and v9's model-written literals. It also goes beyond v5's generic coverage/fact reachability target: the error condition includes both path and exception-trigger conditions. It is **not** a general functional-fault solver. The paper reports 104/198 target exceptions and 21 new NPE bugs; these are author results, not local reproduction. (UnitCon §§1,2.2,4; `B/papers/unitcon/public_evidence/paper_fulltext.txt:21–23,60–81,334–344,625–710`.)

Artifact: verified BSD-3-Clause author source, pinned submodule and Zenodo code/results; heavy Java/Infer setup. Qwen fit: no model is needed, but the artifact does not accept these Python PUTs. **Cheap pilot20/dev gate:** inspect existing candidate sites/traces for a genuine runtime-exception objective and sufficient error preconditions, and check author input-language compatibility. If the target is only wrong functional output or requires a Python port, stop at that eligibility verdict; do not implement a substitute. (`B/audit/reviews/036.json:13–34`.)

**Older foundation, not a newly collected 2025–2026 result:** **SAVIOR: Towards Bug-Driven Hybrid Testing — arXiv, 2019; venue not recorded in the local note.** It prioritizes sanitizer-labelled operations and concolically solves the fault predicate **together with path constraints** on an explored path. This directly separates reaching a site from triggering a fault, a mechanism absent from v31 and not tested by v5's zero-MUTANT-gap experiment. It supplies no functional correctness oracle for arbitrary Python code. The local SAVIOR note records no verified artifact availability; no LLM/Qwen evidence is claimed. A cheap eligibility check would inspect existing pilot20/dev hypotheses for executable trigger predicates and represented path state, without building a concolic engine. (`research/savior/CONCEPT_DIRECTION.md:5–11,19–29,31–35`; `L/analysis/crosshair_gaps_report.md:19`.)

**2. Mokav: Execution-driven Differential Testing with LLMs — Journal of Systems and Software, 2025.** Step b starts from two programs and an equal-output seed; it feeds output and internal execution differences back until it finds a difference-exposing input. The collected notes report 1,255/1,535 Python Codeforces pairs distinguished. This targets an observable difference more directly than v31's fixed templates. Its core is nevertheless close to v7 MUTANT and v9 feedback; the possible increment is paired internal-value differences rather than coarse reach/infect/propagate categories, not a new oracle or solver. (`research/fulltext-batches/batch-05.md:245–259`; `L/RESULTS.md:698–702`.)

Artifact: verified Python author source/data recorded, including C4DET; models include CodeLlama-Instruct-7B, not Qwen. Small-model applicability is plausible, not demonstrated for this Qwen or for PUT-versus-wrong-mutant pairs. **Cheap pilot20/dev gate:** join already saved PUT/alternative executions to count pairs agreeing on public examples but differing on other valid cached inputs; check whether existing paired traces expose informative first differences. No pair potential or no recorded paired state means no-go for a cached-data route. A discrepancy between two untrusted programs remains a candidate, not a bug. (`research/fulltext-batches/batch-05.md:247–259`; `research/savior/CONCEPT_DIRECTION.md:27–29`.)

**3. NeuroTestGen: Neuro-Symbolic Guided Test Generation with Large Language Models — arXiv, 2026.** Step b derives CFG-path constraints, solves numerical paths with Z3, and uses an LLM solver/verifier for object paths before test synthesis. Compared with v21, the substantive difference is solving and supplying input values, not adding another path explanation. Compared with v5/CrossHair, solver-assisted reachability itself is already tried; this paper does not add a functional fault predicate or prove output propagation. (`B/papers/neurotestgen/public_evidence/paper_fulltext.txt:155–170`; `L/RESULTS.md:681–686`.)

Artifact: direct author files were verified despite an inaccessible root, but the documented batch route disables symbolic execution/path solving/verification. Translator limitations include skipped loops, ignored expressions and Real-valued floating-point modelling. Evidence is fixed-code coverage/pass rate, not historical bug discovery. No small-Qwen result is recorded; 80.96% of paths use object handling, so the mechanism often returns reasoning to the model. **Cheap pilot20/dev gate:** count existing target paths fully supported by the documented encoding and compare them with cached CrossHair successes/timeouts. If support is mostly absent, stop; do not treat partial-encoding UNSAT or LLM acceptance as a path proof. (`B/audit/reviews/015.json:13–35`; `B/papers/neurotestgen/public_evidence/paper_fulltext.txt:158–165,305`.)

**4. CASCADE: Detecting Inconsistencies between Code and Documentation with Automatic Test Generation — FSE, 2026.** Steps a/b turn documentation into `if condition → behavior` items, test stubs and completed tests. A separate doc-derived implementation filters reports using fail-to-pass evidence and **no pass-to-fail regression**. This can consider semantics beyond a single-edit catalogue. However, spec decomposition/hypotheses overlap v23, and spec-only alternative implementations overlap v7_mutref: the broad mechanism is not new to this repo. Its explicit transition filter is a useful distinction, primarily for evidence/oracle control rather than reaching difficult inputs. (CASCADE §3; `B/papers/cascade-detecting-inconsistencies-between-code-and-documentation-with-autom-f330aada/public_evidence/paper_fulltext.txt:266–298`; `L/RESULTS.md:725–737`; `memory/linefacts-v23-diagnostic.md:24–31`.)

Artifact: MIT author implementation, dataset and cached results verified; models GPT-4.1-mini/GPT-4o-mini, no Qwen evidence. Dataset includes documentation errors; code and tests may share an incorrect assumption. **Cheap pilot20/dev gate:** use existing spec-generated reference programs and saved tests to tabulate pass/fail transitions and disagreement with dev evaluation outcomes. Check whether any retained candidate/input adds a task beyond existing witnesses. If no such cached artifacts exist, the CPU-only benefit check is unavailable, not positive. (`B/audit/reviews/056.json:10–35`; `L/RESULTS.md:655,725–737`.)

**5. Directed Greybox Fuzzing via Large Language Model (HGFuzzer) — arXiv, 2025.** Step b converts target call-chain/path constraints into generated harnesses, seeds and target-specific mutators, then uses directed greybox fuzzing. The collected notes report 17/20 known vulnerabilities triggered. Unlike v31, it searches beyond a fixed one-edit neighbourhood. Unlike v21's inspected flow information, there is an executable search component. V5 already asked for generator strategies, so the broad “generate programs rather than literals” idea is not new; the untried detail is target-specific harness/mutator synthesis combined with native directed fuzzing. (`research/fulltext-p0-notes.md:75–87`; `research/fulltext-batches/batch-04.md:165–173`; `L/PIPELINES.md:291–325`.)

Artifact: recorded verified Zenodo source and per-CVE outputs; C/C++ libraries, Claude-3.5-Sonnet, no Qwen evidence. **Cheap pilot20/dev gate:** inspect existing sites and input schemas for a compatible target/harness route and whether saved targeted generators already provide nontrivial structural variation.
