# VR12 public-source eligibility census and saved-round1 OBS check

Before new native OBS classification: enumerate the completed V85 archive using
the frozen VR9 `bind()` function and its existing three families. The source-only
census contains 17 eligible tasks; six were already used by VR8/VR9. Select all
11 fresh eligible tasks: 12, 27, 48, 64, 67, 80, 89, 112, 118, 140, 162. This is
a census, not a sample chosen by detected bugs. Twenty distinct eligible fresh
tasks are unavailable without changing the binder. Keep the old six separate.

Classify the saved round1 input tuples on public PUT source using frozen VR9
native workers. No canonical source, reference predictions or final bug labels
enter these workers. For each task choose a supported binding preferring one
with no observed true state in saved round1, then use SHA256(card ID + site) to
break ties. Order tasks by SHA256(task ID). Preserve observed false, unknown and
unreached independently; uncovered is not proof of a true defect hypothesis.

Materialize public task/binding/round1 records and the ten saved reference
receipts per selected task, with archive/freeze provenance. Reference programs
remain scoring resources; no new strategy, model or oracle calls are made here.
Any grading asset is copied opaquely by the controller owner for final scoring.

Disclosure: before the reviewer restricted selection to public OBS evidence,
an earlier feasibility request asked for saved round1 bug-ceiling strata. Those
labels were mechanically computed from old final scoring records. They do not
enter the eligibility predicate, this complete-census selection, OBS worker
jobs or deterministic binding selection. Treat the cohort as development-informed
and disclose that exposure; do not call it blinded or held out.

The parent will register and review a new copied pipeline before any model run.
Four arms at K=1 have a conservative completion cap N*4*(2 strategies + 1
expected-output request), hence 132 for N=11; three arms would cap at 99.
Shared exact-request replay may reduce physical usage but cannot raise the cap.
The original six tasks alone have exact VR8/VR9 strategy pools; the fresh census
requires fresh strategy requests. This plan makes no efficacy claim.
